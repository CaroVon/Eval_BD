## 2. G1 主张的变化

方案中的 G1 门槛：至少一个任务、至少一个高位宽版本满足 |A|/|P| <= 0.6，确定性验证通过，端到端加速比 >= 1.5。

| 门槛 | 结果 | 判断 |
|---|---|---|
| \|A\|/\|P\| <= 0.6 | GSM8K Q8_0：Qwen-3B 0.519、7B 0.317、14B 0.398、Llama-8B 0.420、Phi 0.414。Q6_K 0.69-0.90；MMLU-Pro Q8_0 0.63-0.76 | 通过（仅 Q8_0、GSM8K） |
| 确定性 | 批不变 fp32 下四层通过；compiled 模式要逐模型检查；bf16 会产生大量精确平局 | 通过，但对象是规范执行 |
| 加速比 >= 1.5 | 端到端实测（完整生成时间 / (全量 prefill + 续写)，batch 256）：GSM8K Q8_0 0.87-1.22x，Q6_K 0.68-0.86x，MMLU-Pro 0.65-1.08x。按 token 估算的数字（小 batch 约 2.2x）和重锚定回放（约 1.5x）都不是端到端实测 | **当前实现下不通过**（更正，见第 7 节） |

据此，主张相对方案有以下变动：
1. **认证对象**：从"量化模型"收窄为"规范的批不变执行（轨道 A）"。
   - 部署用的 GGUF 在 llama.cpp 下不满足 prefill/解码一致（续写检查 217/400），且与 vLLM 的输出差异取决于模型家族。
   - 方案 5.5 预留了这条退路。
2. **实践收益的范围**：从"高位宽版本"（方案预期 Q8_0 和 Q6_K 都有显著排除）收窄为"Q8_0，以及小有效 decode batch 下的 Q6_K"。
   - 方案假设 prefill/解码成本比是常数。实测它与 decode batch 成正比，因为每个 decode step 的耗时近似固定。
   - 所以主张必须附带执行场景：小 batch，即受显存限制、大模型或长输出。
3. **任务**：MMLU-Pro 并非"中等长度"（平均 466 token，7% 触达 1,024 上限），在这个任务上没有实践收益。
4. **证书**：真实的伤害和修复近似对称，所以只认证伤害率在修复多时无法精确到 tau（已证明）。
   - 新增净证书，但它需要接近全量的审计。
   - 下界显示这是固有代价：任何同等水平的方法都至少需要净证书所用审计率的 70-90%。
5. **新增的支撑贡献**：margin 噪声定律、成本定律、净证书及其下界、确定性方面的发现（bf16 平局、逐模型的编译模式）。

## 4. 能否实现最初的论文层面结论

方案的论文层面结论是："精确信息改变问题规模……并在量化阶梯的高位宽版本上转化为可测量的端到端计算节省。"
- 理论部分（结构-预测分离、上下界）可以完整实现，不受实验结果影响。
- "可测量的端到端节省"只能以收窄的形式实现：Q8_0（以及部分 Q6_K），在小有效 decode batch 的规范执行下。
- 大 batch 离线评测小模型时，节省很小，或者 B1 更便宜。
- 最能支撑收窄主张的实验是一个天然受显存限制的大模型（32B 多卡），说明小 batch 是真实场景，而不是人为设置。

## 5. 与 ICML 投稿要求的差距（评估，非结论）

形式要求（篇幅、匿名、复现材料）可以满足。真值矩阵、脚本和证书代码已经齐全，可作为配套数据集发布。

实质性的强项：
- 有限样本、模型无关的认证理论，上下界匹配，并有净证书的扩展。
- 精确筛查在 13 个真值矩阵、5 个家族上零违例。
- margin 定律（46 例，比值 0.74-1.12）是一条可复现的经验规律。
- 基线覆盖完整，并如实报告了负面结果。

主要风险（审稿人可能的质疑）：
1. 实践收益只在窄场景成立。没有天然的小 batch 实验时，容易被认为是人为设置。
2. 认证对象是规范执行，而不是实际部署的制品，削弱了应用意义。
3. 新颖性：teacher-forced 验证即推测解码，下界是 Le Cam 两点论证。必须以分离结果和精确信息的刻画为核心，方案 5.3 已列出不主张的内容。
4. tau = 0.05 时多数版本的伤害证书无法通过；净证书接近全量审计。
5. 方案原定的 3 个不同家族父模型和 MGSM 语言切片尚未按定稿完成。

判断：
- 按方案门槛：G1 的前两条通过，加速比一条在当前实现下不通过（第 7 节）；G3 有条件通过。G1 不通过时，方案的预案是收窄主张，而不是转投。
- 录用把握取决于两件事：一是论文定位为"认证理论 + 经验规律"，把实践收益限定在明确的场景；二是补上第 6 节的 1-3 项。

## 7. 更正：端到端实测加速比（同日补充）

数据来自各真值矩阵的 `screen/<version>/summary.json`（`seconds`，batch 256，A100，fp32 批不变）。

| 指标 | GSM8K Q8_0（6 个父模型） | GSM8K Q6_K | MMLU-Pro Q8_0 |
|---|---|---|---|
| 加速比 = full / (prefill + cont) | 0.87-1.22 | 0.68-0.86 | 0.74-1.08 |
| 续写的解码 token 占比 | 0.22-0.38 | 0.50-0.73 | 0.51-0.59 |
| 续写的时间占比 | 0.38-0.63 | 0.70-0.91 | 0.66-0.81 |
| 全量 prefill 的时间占比 | 0.33-0.67 | 0.32-0.67 | 0.26-0.57 |

这里的 full、prefill、cont 分别是完整生成、全量 prefill 和续写的耗时，占比都相对完整生成。

原因有三条，都来自当前的实现和配置，不是方法本身的限制：
1. **两次 prefill。** 筛查先 prefill 提示词加整段父模型输出（prefill token 约为解码 token 的 1.4 倍）。续写又作为新请求，把提示词和前缀重新 prefill 一遍。
2. **每个 decode step 的耗时固定（sec. 36）。** 续写的序列更少，batch 填不满，时间由步数决定，而不是由 token 数决定。所以省下 66% 的 token 只省下 42% 的时间（Qwen-3B Q8_0）。
3. **fp32 执行**（为了避免 bf16 平局）让 compute-bound 的 prefill 变贵。

对 G3 的影响：G3 的同等计算量比较用的是 token 成本模型（r），没有计入 batch 占用率这类效应。所以需要用墙钟时间重新校准，再确认 G3 的比值。

## 8. 实现变体的实测结果（同日补充，RESULTS.md sec. 46-48）

- **G2（按原口径）：** 只有 GSM8K 上 Qwen 3B/7B/14B 的 Q8_0（以及 14B 的 Q6_K）通过。Llama、Phi、SmolLM2 不通过。MMLU-Pro 上没有任何版本可以认证。
- **墙钟成本模型（误差 <= 2%）：** 每个 decode step 的固定成本占主导。在 batch 256、同等墙钟时间下，G3 不成立：Q8_0 的比值为 0.94-1.40x，只有 Qwen-14B 在 b = 0.8 时达到 1.87x。G1 表 2 的比值是按 token 成本模型算的。
- **实现变体：** prefix caching 和 bf16 都保持 Lemma 3 精确成立，但最好的变体只到 1.08x。
- **结论：** batch 256 下达不到 1.5x，不是由我们的实现选择造成的，而是方案 E3 在这个引擎成本结构下的必然结果。按方案 5.5 收窄到"小有效 batch"场景是有依据的；要验证这个场景，需要 batch 32 的墙钟数据或 32B 实验。
